# 中庭 · 本地缓存方案（草案 v1）

> 目标：GitHub 偶发失败（超时 / 限流 / 代理抖动）时内容照常显示；日常浏览不再反复消耗 API 配额。
> 约束：全部在一个项目里搞定，不启任何数据库服务。

## 一、核心思路：内存 + 磁盘两级缓存

| 层   | 载体                         | 作用                                         |
| ---- | ---------------------------- | -------------------------------------------- |
| L1   | 进程内存                     | 毫秒级命中，频繁访问零成本                   |
| L2   | `data/cache/*.json` 磁盘文件 | 重启不丢；dev 重启 / 桌面 App 重启后依旧秒开 |
| 回源 | GitHub API                   | 只在 TTL 到期或主动刷新时发生                |

读取顺序：内存 → 磁盘 → 回源；回源成功 → 同步写回两层。

## 二、关键策略

1. **失败即端旧数据**：回源失败 / 超时 / 限流时，直接返回上次成功的数据（哪怕已过期），不再让页面出空。
2. **写入即失效**：发文章、改书签、传图、改名、删除等写操作完成后，相关键立即失效（写后读一致）。
3. **原子落盘**：临时文件 + rename，崩溃/断电不产生坏文件；坏文件自动忽略并重取。
4. **并发防抖**：同一键同时只发起一个请求（多标签页/多组件共享结果）。

## 三、覆盖范围与节奏（先做这四块）

| 数据                  | 键        | TTL     | 说明                   |
| --------------------- | --------- | ------- | ---------------------- |
| 文章列表 + 文件夹树   | `content` | 10 分钟 | 写操作立即失效         |
| 画廊（相册 + 图片）   | `gallery` | 5 分钟  | 上传/改名/删除立即失效 |
| 工具房清单            | `tools`   | 5 分钟  | 增删改立即失效         |
| 工坊展品清单          | `demos`   | 5 分钟  | —                      |
| 提交时间（展品/图片） | `commits` | 24 小时 | 内容寻址，几乎不变     |

## 四、为什么不选数据库

- **better-sqlite3 等原生模块**：需要编译，Electron 打包需重编译，维护成本高。
- **外部数据库服务**：违背约束，且单机单进程、数据量仅几百 KB，完全没必要。
- **演进预留**：Node 22 起自带 `node:sqlite`（纯文件、零服务），如未来需要检索/历史，可平滑升级。

## 五、边界（v1 不做）

- 文章正文/展品源码的离线全文库（v2 可选）。
- 跨设备同步缓存（每端各自本地存储）。

## 六、验收标准

1. 模拟 GitHub 失败（断网 / 坏令牌）时，四个房间内容依然完整显示（上次数据）。
2. 正常浏览 10 分钟内的重复访问，GitHub 读请求为零（TTL 内）。
3. dev / 桌面 App 重启后，首屏内容直接从磁盘命中。
4. 写操作（发布文章/改书签/传图）后立即能看到最新数据（失效链路通）。

## 七、实施步骤（一次交付）

1. 新增 `src/lib/cache.ts`（两级缓存 + 原子写 + 防抖 + 失效 API）。
2. 接入四类数据源；写接口挂失效钩子。
3. 巡检脚本新增「缓存命中」检查项；实测验收。
